# Reproducibility

This document describes how to reproduce the analysis pipeline and verify the reported results of the FER Reliability Benchmark.

The goal of reproducibility is to ensure that the analysis can be independently inspected, rerun, and compared against the evidence generated by the validated pipeline.

---

## 1. Reproducibility Scope

The benchmark is organized as a sequential analysis pipeline.

The general workflow is:

```text
Input Data
    ↓
Metadata Preparation
    ↓
Representation / Embedding Extraction
    ↓
Representation Analysis
    ↓
Trajectory Analysis
    ↓
Event Ordering
    ↓
Statistical Validation
    ↓
Early-Warning Analysis
    ↓
Horizon Analysis
    ↓
Robustness / Sensitivity Analysis
    ↓
Cross-Expression Validation
    ↓
Cross-Identity Validation
    ↓
Representation Validation
    ↓
Final Synthesis
```

Each stage produces evidence that can be used by subsequent stages.

The final synthesis stage reads the existing evidence and does not rerun or re-estimate the preceding analyses.

# 3. Environment

The analysis should be executed in a dedicated Python environment.

The validated analysis was executed in an environment named:

```text
plate_gpu
```

The exact Python version, package versions, GPU configuration, and model dependencies should be recorded in the repository before claiming exact reproducibility.

For example:

```bash
conda activate plate_gpu
```

Then verify the Python installation:

```bash
python --version
```

and verify the installed packages:

```bash
pip list
```

A reproducible environment should preferably be captured using an environment file or dependency specification.

For example:

```bash
pip freeze > requirements-lock.txt
```

or, for a Conda environment:

```bash
conda env export > environment.yml
```

These files should be committed to the repository when they are available and stable.

---

# 4. Input Data

The benchmark requires the original input dataset and the corresponding image sequences.

The input data should not be modified after the validated analysis has been performed.

For reproducibility, the following should be documented:

- dataset name;
- dataset version;
- source;
- preprocessing procedure;
- image organization;
- identity organization;
- expression organization;
- viewpoint organization;
- number of expected viewpoints;
- frontal viewpoint definition.

Large datasets should generally not be committed directly to the Git repository.

Instead, the repository should document how the data can be obtained and where it must be placed locally.

# 5. Fixed Configuration

The validated benchmark uses fixed configuration values.

The reported configuration includes:

```text

Fixed C threshold: 0.0023708
Frontal viewpoint: 107
```

These values should remain unchanged when reproducing the validated analysis.

If a parameter is changed, the resulting analysis should be considered a new experimental run rather than an exact reproduction of the validated results.

# 8. Evidence-Based Final Synthesis

The final synthesis stage is intentionally separated from the earlier analytical stages.

Its purpose is to integrate existing evidence.

The final synthesis:

```text
does NOT rerun Stage 1–9
does NOT re-estimate previous statistics
does NOT modify previous results
does NOT replace missing evidence
```

Instead, it:

```text
discovers available evidence
        ↓
reads existing CSV/JSON files
        ↓
inspects schemas
        ↓
extracts compatible fields
        ↓
normalizes relevant quantities
        ↓
builds synthesis tables
        ↓
builds final claims
        ↓
generates final plots
        ↓
writes the final report
```

This separation is important because the final synthesis should remain an evidence-integration step rather than becoming another independent reanalysis.

---

# 9. Dynamic Schema Detection

Different analysis outputs may use different column names for similar quantities.

For example, an A-before-B result may be represented by:

```text
A_before_B
```

or:

```text
A_before_B_percent
```

or:

```text
A_before_B_rate
```

The final synthesis should therefore inspect the available schema before extracting a value.

The expected behavior is:

```text
Read file
    ↓
Inspect column names
    ↓
Identify compatible field
    ↓
Extract value
    ↓
Normalize units
    ↓
Record source field
```

This prevents the final synthesis from failing simply because an equivalent measurement has a different column name.

The source field used for an extracted result should preferably be retained in the final evidence or metadata.

---

# 10. Stage 4 — Early Warning

The early-warning stage evaluates the ordering between the representation-related event and recognition failure.

The main relationship is:

```text
A → B
```

where:

```text
A = predefined representation-related event
B = predefined recognition-failure event
```

The main quantity is the proportion of valid sequences in which:

```text
A occurs before B
```

The stage also evaluates lead distance and warning-model performance.

---

# 11. Stage 5 — Horizon Analysis

The horizon analysis evaluates whether the early-warning signal remains available at different viewpoint distances.

The analysis evaluates quantities such as:

```text
horizon
warning count
warning rate
median lead
permutation evidence
```

The purpose is to determine how far before recognition failure the warning relationship remains detectable.

---

# 12. Stage 6 — Robustness and Sensitivity

The robustness stage examines whether the main relationship remains stable under alternative analytical conditions.

The analysis includes evidence from:

```text
threshold sensitivity
sustained-viewpoint conditions
metric sensitivity
warning horizons
bootstrap analysis
permutation analysis
robustness scoring
```

A robust result should not depend entirely on one arbitrary analytical configuration.

---

# 13. Stage 7 — Cross-Expression Validation

Cross-expression validation evaluates whether the observed relationship generalizes across the evaluated expression groups.

The analysis distinguishes between:

```text
all available expression groups
```

and:

```text
primary eligible expression groups
```

Primary generalization claims should be based on the predefined eligible groups.

Small or otherwise ineligible groups should remain descriptive and should not be used as primary evidence for generality.

---

# 14. Stage 8 — Cross-Identity Validation

Cross-identity validation evaluates whether the observed relationship remains present across identity conditions.

The analysis includes:

```text
identity-level A-before-B rates
median lead
mean lead
confidence intervals
horizon analysis
bootstrap analysis
robustness scores
paired comparisons
```

The purpose is to determine whether the result is restricted to a particular identity condition or remains present across the evaluated identity groups.

---

# 15. Stage 9 — Representation Validation

Representation validation examines the behavior of the representation directly.

Relevant outputs include:

```text
representation_view_metrics.csv
representation_boundaries.csv
representation_sequence_summary.csv
representation_expression_summary.csv
representation_viewpoint_profile.csv
representation_pairwise_summary.csv
representation_pairwise_test.csv
representation_paired_identity.csv
representation_identity_tests.csv
representation_lead_lag.csv
representation_bootstrap.csv
representation_fdr.csv
```

The analysis includes same-expression versus rival-expression representation comparisons, representation lead/lag analysis, identity comparisons, bootstrap analysis, and false-discovery-rate analysis.

# 17. Reproduction Procedure

A new researcher should follow this general procedure.

## Step 1 — Clone the repository

```bash
git clone <REPOSITORY_URL>
cd FER-Reliability-Benchmark
```

Replace `<REPOSITORY_URL>` with the actual repository address.

---

## Step 2 — Create the environment

If an environment specification is provided:

```bash
conda env create -f environment.yml
```

Then activate it:

```bash
conda activate plate_gpu
```

If a requirements file is provided instead:

```bash
pip install -r requirements.txt
```

---

## Step 3 — Prepare the dataset

Place the benchmark data in the documented local data directory.

Do not commit private, restricted, or very large datasets directly into the repository.

Verify that the expected image sequences and metadata are available before starting the analysis.

---

## Step 4 — Verify the configuration

Before execution, verify:

```text
A threshold = 13.43702602
C threshold = 0.0023708
frontal viewpoint = 107
expected viewpoints = 215
```

---

## Step 5 — Execute the pipeline

Run the stages in the documented order.

Each stage should complete successfully before dependent stages are executed.

After each stage, verify that its expected evidence files have been generated.

---

## Step 6 — Verify Evidence

Before running the final synthesis, inspect:

```text
analysis/
```

and verify that the expected evidence directories and files are present.

The final synthesis should report which stages have detectable evidence.

---

## Step 7 — Run Final Synthesis

The final synthesis reads existing evidence.

It should be run only after the preceding evidence has been generated.

For example:

```bash
python analyze_final_synthesis.py
```

The exact filename should match the implementation stored in the repository.

---

## Step 8 — Inspect Final Outputs

After successful execution, inspect:

```text
analysis/final_synthesis/
```

In particular:

```text
final_key_results.csv
final_publication_table.csv
final_claims.csv
final_stage_status.csv
final_synthesis_report.json
```

and the generated plots.

# 18. Reproducibility Verification

A reproduction should not be considered successful merely because the scripts execute without errors.

A stronger verification should compare:

1. stage completion status;
2. number of valid sequences;
3. number of expressions;
4. A-before-B rates;
5. median lead values;
6. horizon results;
7. robustness results;
8. cross-expression results;
9. cross-identity results;
10. representation-level results;
11. final synthesis claims.

Small numerical differences may occur because of differences in:

- hardware;
- numerical libraries;
- random seeds;
- GPU implementation;
- dependency versions.

Such differences should be documented rather than silently ignored.

---

# 19. Randomness and Seeds

Any stochastic procedure should use an explicitly recorded random seed whenever possible.

This is particularly important for:

```text
bootstrap procedures
permutation tests
random sampling
model initialization
```

If a seed is not fixed by the original implementation, exact numerical reproduction may not be possible.

In such cases, reproduction should focus on whether the qualitative and statistical conclusions remain consistent.

# 21. Git Commit and Version Tracking

Each validated analysis should be associated with a Git commit.

Before running the pipeline, record:

```bash
git status
git rev-parse HEAD
```

The commit hash should be saved with the final analysis record.

This allows a future researcher to determine exactly which version of the code produced the reported outputs.

---

# 22. Do Not Overwrite Validated Evidence

Existing validated evidence should not be overwritten without documentation.

If a new analysis configuration is tested, create a separate run or clearly document the change.

For example:

```text
analysis/
├── final_synthesis/
└── experimental_runs/
    ├── run_001/
    ├── run_002/
    └── run_003/
```

This prevents experimental changes from being confused with the validated benchmark results.

---

# 23. Missing Evidence

A missing stage should be reported as missing.

It should not be silently reconstructed from unrelated files.

For example:

```text
Stage 1 — NOT_FOUND
Stage 2 — NOT_FOUND
Stage 3 — NOT_FOUND
Stage 4 — DONE
...
```

The final synthesis should preserve this distinction.

Missing evidence is not equivalent to evidence of absence.

---

# 24. Scientific Reproducibility

Reproducibility has two different meanings in this project.

### Computational reproducibility

The same code, configuration, data, and environment produce equivalent outputs.

### Scientific reproducibility

An independent researcher can understand the methodology, reproduce the analysis, and evaluate whether the same scientific conclusion is supported.

Both are important.

---

# 25. Interpretation During Reproduction

The reproduction process should preserve the distinction between:

```text
observation
```

```text
statistical association
```

```text
predictive utility
```

and:

```text
causality
```

In particular:

```text
A-before-B precedence
```

should not be interpreted as proof that A causes B.

The benchmark evaluates ordering and predictive evidence within the tested experimental design.

---

# 26. Limitations of Exact Reproduction

Exact numerical reproduction may be affected by:

- different hardware;
- different GPU implementations;
- dependency versions;
- floating-point behavior;
- stochastic procedures;
- model implementation differences;
- dataset changes;
- preprocessing differences.

Therefore, a successful reproduction should be evaluated using both numerical agreement and scientific consistency.

# 28. Reproducibility Principle

The central reproducibility principle of this project is:

```text
Same data
+
Same preprocessing
+
Same model
+
Same configuration
+
Same code version
+
Same environment
+
Same execution order
=
Comparable results
```

If any of these components changes, the resulting analysis should be treated as a new run and documented accordingly.

---

# 29. Final Statement

The repository is intended to make the complete analysis traceable from input data to final scientific claims.

The final synthesis is an evidence-integration step and should not be used to hide missing analyses or replace unavailable evidence.

A reproducible result requires not only executable code, but also transparent documentation of:

```text
data
→ configuration
→ code
→ environment
→ execution
→ evidence
→ synthesis
→ interpretation
```

The final scientific claims should always be traceable back to the underlying stage-specific evidence.
